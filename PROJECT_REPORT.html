Abstract

Conventional cloud storage and file-sharing systems expose user data to substantial privacy risks because encryption keys and plaintext contents are typically stored or processed directly on centralized backend servers. In the event of a database compromise, insider threat, or server infrastructure breach, sensitive files can be decrypted and exposed without user authorization.

This project presents CryptaShare: Secure File Exchange Portal, a zero-knowledge web platform designed to eliminate centralized trust. Files are encrypted locally inside the uploader’s browser prior to transmission using AES-256-GCM (Galois/Counter Mode) via the browser-native Web Crypto API. The symmetric key is generated strictly in browser volatile memory and appended to the URL fragment (#key=...). Because URL fragments are omitted from HTTP requests by web specifications (RFC 3986), the backend server and MySQL database never receive, log, or store the decryption key or plaintext payload.

Furthermore, the system implements ephemeral access controls, including configurable time-based expirations (15 minutes to 7 days), server-enforced download counters (such as single-use self-destruct limits), and instantaneous link revocation paired with immediate physical ciphertext purges from disk. Access and revocation tokens are protected using 256-bit cryptographically secure pseudorandom generators (CSPRNG), and only their SHA-256 digests are stored in MySQL. The system was implemented in Java 21 LTS, Spring Boot 3.3.4, and vanilla web standards, achieving a verified 24-test automated test suite with zero failures.

Chapter 1: Introduction

1.1 Background & Motivation

In modern digital workflows, individuals and organizations frequently exchange confidential documents such as financial statements, medical records, legal contracts, source code, and identification credentials. Traditional cloud storage and file transfer solutions (e.g., standard Google Drive, Dropbox, or WeTransfer links) operate under a server-mediated trust paradigm. In this model, unencrypted files or server-managed encrypted files are uploaded directly to centralized servers. The cloud provider retains access to the decryption keys or the raw plaintext.

This centralized model creates significant security vulnerabilities. Server infrastructure is exposed to database leaks, configuration errors, unauthorized insider inspection, and legal subpoenas. When a breach occurs, all stored plaintext files are compromised simultaneously.

1.2 Problem Statement

To guarantee true confidentiality and data privacy, a secure file sharing portal must adhere to the Zero-Knowledge Principle: the hosting server and database must store only encrypted data and have mathematically zero access to the decryption keys or plaintext content. Existing open-source implementations frequently suffer from several architectural flaws:

  • Encryption keys are accidentally passed as URL query parameters (e.g., ?key=...), exposing them in server access logs and web proxy caches.
  • Plaintext access tokens are stored directly in databases, enabling attackers who dump database tables to access all files.
  • File upload links remain active indefinitely without granular lifecycle control, such as self-destructing download limits or immediate revocation.
  • User-provided file paths are used directly on the server filesystem, creating path traversal vulnerabilities.

1.3 Project Objectives

The primary objectives of this project are:

  1. Client-Side Zero-Knowledge Encryption: Implement 256-bit AES-GCM encryption in the user's browser using native Web Crypto APIs before any file data leaves the local workstation.
  2. URL Fragment Isolation: Place the secret decryption key exclusively in the URL fragment (#key=...) so that web clients never transmit the key across the network to the server.
  3. Cryptographically Secure Token Hashing: Generate 256-bit access and revocation tokens and store only their SHA-256 digests in MySQL.
  4. Ephemeral Access Control: Enforce configurable expiration durations (15m to 7 days), atomic download counters (single-use self-destruct limits), and instantaneous revocation that purges physical files from disk.
  5. Production Engineering: Implement the solution using Java 21 LTS, Spring Boot 3.3.4, and MySQL, supported by automated unit and integration test suites.

Chapter 2: Literature Survey & Theoretical Background

2.1 Symmetric Cryptography & Authenticated Encryption

Symmetric encryption algorithms employ the same secret key for both data encryption and decryption. Early modes such as Electronic Codebook (ECB) and Cipher Block Chaining (CBC) provided confidentiality but failed to guarantee data integrity. In CBC mode, an adversary capable of intercepting ciphertext could perform bit-flipping attacks without detection unless an auxiliary Message Authentication Code (such as HMAC-SHA256) was explicitly applied.

To resolve this vulnerability, modern cryptographic standards utilize Authenticated Encryption with Associated Data (AEAD). The foremost standard is AES-GCM (Galois/Counter Mode), standardized in NIST SP 800-38D. AES-GCM combines counter-mode encryption (providing confidentiality) with universal hashing over a binary Galois Field $GF(2^{128})$ to produce a 128-bit authentication tag.

Mathematical Formulation of AES-GCM
Given a plaintext $P$, a 256-bit symmetric key $K$, and a unique 96-bit Initialization Vector $IV$:
$$C = \text{AES-CTR}_K(IV, P)$$ $$T = \text{GHASH}_H(\text{AAD} \mathbin{\Vert} C \mathbin{\Vert} \text{len}(\text{AAD}) \mathbin{\Vert} \text{len}(C)) \oplus E_K(J_0)$$ Where $C$ is the ciphertext, $T$ is the 128-bit authentication tag, and $H = E_K(0^{128})$ is the hash key. Any modification to $C$ or $IV$ results in tag mismatch and immediate decryption rejection.

2.2 URL Fragment Protocol Specification (RFC 3986)

According to the Internet Engineering Task Force (IETF) Uniform Resource Identifier (URI) Generic Syntax specification (RFC 3986, Section 3.5), a URI is structured into components: 

URI = scheme ":" ["//" authority] path ["?" query] ["#" fragment]

The specification states that "the fragment identifier component of a URI allows indirect identification of a secondary resource by reference to a primary resource... fragment identifiers are processed solely by the user agent (browser) and are never transmitted in HTTP request lines or headers."

This project leverages this RFC standard as a security boundary: the secret decryption key is stored after #key=..., ensuring that no web server, CDN, proxy, or backend database ever observes the key.

Chapter 3: System Requirements Specification

3.1 Functional Requirements

  • FR-1 (Client Encryption): The system must encrypt files using AES-256-GCM locally in the client browser prior to transmitting data.
  • FR-2 (Key Handling): The browser must generate keys locally and embed them exclusively in the URL fragment; the backend must reject any request that attempts to pass encryption keys.
  • FR-3 (Token Hashing): The backend must generate 256-bit random access and revocation tokens and store only their SHA-256 hashes in MySQL.
  • FR-4 (Lifecycle Enforcement): The system must automatically reject download requests for expired, revoked, or download-exhausted links with HTTP 410 Gone.
  • FR-5 (Immediate Revocation): When an uploader presents a valid revocation token, the system must set the revoked status and delete the physical ciphertext file from disk.
  • FR-6 (In-Browser Decryption): The recipient interface must stream the ciphertext, verify the GCM authentication tag, and trigger a native download preserving the original filename and MIME type.

3.2 Non-Functional Requirements

  • NFR-1 (Security & Zero Knowledge): Even with root database access, a server administrator must be unable to decrypt any stored file.
  • NFR-2 (Performance): Server CPU utilization remains minimal because cryptographic computations are offloaded to client runtimes.
  • NFR-3 (Integrity): Any byte-level modification of ciphertext or IV must cause immediate decryption failure.
  • NFR-4 (Portability): Operates on standard desktop and mobile browsers supporting Web Crypto API without external plugins or frameworks.

4.2 Detailed Sequence Workflow

The system operates across three primary lifecycles:

  1. Encryption & Upload Phase:
    1. The client generates a 256-bit key $K$ and a 12-byte IV.
    2. The plaintext $P$ is encrypted into ciphertext $C$ and authentication tag $T$.
    3. The payload $IV \mathbin{\Vert} C \mathbin{\Vert} T$ is transmitted via POST /api/files/upload.
    4. The backend generates 256-bit random tokens $T_{access}$ and $T_{revoke}$, hashes them with SHA-256, stores the ciphertext to a UUID file on disk, and writes metadata to MySQL.
    5. The client constructs the sharing link with $T_{access}$ as a query parameter and $K$ as the URL fragment.
  2. Verification & Download Phase:
    1. The recipient opens the link; the browser extracts $T_{access}$ and $K$.
    2. The browser calls GET /api/files/meta?token=... to verify status.
    3. The server queries token_hash = SHA-256(T_{access}), enforcing expiration, revocation, and download count checks.
    4. The recipient calls GET /api/files/download?token=...; the server increments the download counter and streams the ciphertext.
    5. The recipient browser extracts the 12-byte IV, imports $K$, decrypts the payload, and triggers an in-browser file download.
  3. Revocation & Purge Phase:
    1. The uploader submits $T_{revoke}$ to POST /api/files/revoke.
    2. The server computes SHA-256(T_{revoke}) and locates the database record.
    3. The server updates revoked = TRUE and permanently deletes storage_filename from disk.

Chapter 5: Implementation Details

5.1 Client-Side Cryptography (crypto-utils.js)

The client-side module manages AES-256-GCM key generation, file encryption, packaging of the 12-byte IV, and Base64URL conversions: 

// Generates a 256-bit AES-GCM key in browser memory
async generateAesKey() {
  return await window.crypto.subtle.generateKey(
    { name: "AES-GCM", length: 256 },
    true, // Extractable for encoding into URL fragment
    ["encrypt", "decrypt"]
  );
}

// Encrypts file: prepends 12-byte IV to the ciphertext payload
async encryptFile(file, key) {
  const plaintextBuffer = await file.arrayBuffer();
  const iv = window.crypto.getRandomValues(new Uint8Array(12));
  const ciphertextBuffer = await window.crypto.subtle.encrypt(
    { name: "AES-GCM", iv: iv },
    key,
    plaintextBuffer
  );
  const combined = new Uint8Array(iv.length + ciphertextBuffer.byteLength);
  combined.set(iv, 0);
  combined.set(new Uint8Array(ciphertextBuffer), iv.length);
  return new Blob([combined], { type: "application/octet-stream" });
}

5.2 Server-Side Token Generation & Hashing (SecurityTokenService.java)

Tokens are generated using Java's cryptographically secure pseudorandom number generator (SecureRandom) and hashed via SHA-256 before storage: 

@Service
public class SecurityTokenService {
    private final SecureRandom secureRandom = new SecureRandom();

    public String generateSecureToken() {
        byte[] randomBytes = new byte[32]; // 256-bit entropy
        secureRandom.nextBytes(randomBytes);
        return Base64.getUrlEncoder().withoutPadding().encodeToString(randomBytes);
    }

    public String hashToken(String token) {
        return HashUtils.sha256Hex(token);
    }
}

5.3 Storage Service & Path Traversal Mitigations (FileStorageService.java)

The storage subsystem isolates files from the web root and enforces boundary checks to neutralize directory traversal attacks: 

public Path resolveAndValidate(String filename) {
    Path resolvedPath = storageDirectory.resolve(filename).normalize();
    if (!resolvedPath.startsWith(storageDirectory)) {
        throw new FileStorageException("Path traversal attempt detected!");
    }
    return resolvedPath;
}

Chapter 7: Security Analysis & Limitations

7.1 Threat Model Analysis

Threat Scenario Attack Vector System Defense Mechanism
Database Leak Adversary steals SQL database dump. Tokens are stored as SHA-256 hashes; ciphertext is on disk; keys are absent. Attackers cannot construct valid links or decrypt files.
Filesystem Compromise Adversary gains access to server storage. Files are stored as AES-256-GCM ciphertext without keys or plaintext filenames. Data remains unreadable.
Man-in-the-Middle (MITM) Adversary intercepts network traffic. Under HTTPS/TLS, traffic is encrypted. Furthermore, the URL fragment (#key=...) is never sent over HTTP.
Data Tampering Attacker alters ciphertext bits on server. AES-GCM authentication tag check fails during client decryption, throwing an integrity error and blocking file release.
Path Traversal Attacker submits filenames with ../../. The server generates random UUIDs for physical filenames and validates normalized canonical paths.

7.2 Academic Limitations

  • Browser Memory Constraints: Very large files (>1 GB) read into client RAM as an ArrayBuffer can cause memory pressure on low-spec client devices. (Production systems use Web Streams with chunked AEAD).
  • Server Integrity Assumption: If the web hosting server is compromised, an attacker could tamper with served JavaScript (crypto-utils.js). In production, this is mitigated by Content Security Policy (CSP) and Subresource Integrity (SRI).

Chapter 8: Conclusion & Future Scope

8.1 Conclusion

The Secure File Exchange Portal (CryptaShare) demonstrates that zero-knowledge file sharing can be achieved using native browser standards and lightweight backend infrastructure. By performing authenticated AES-256-GCM encryption in the browser, storing secret keys exclusively within the URL fragment, and maintaining only SHA-256 digests in MySQL, the system eliminates centralized trust.

The platform incorporates ephemeral lifecycle controls, including time-based expiration, atomic download limits, and physical disk purges upon revocation. Built on Java 21 LTS and Spring Boot 3.3.4, the implementation passed all 24 automated unit and integration tests, providing a robust architecture suitable for technical evaluation.

8.2 Future Scope

  • Web Stream AEAD Chunking: Implementing TransformStream to encrypt files in 64 KB chunks, enabling multi-gigabyte file transfers with minimal RAM consumption.
  • Password-Derived Key Protection: Adding an optional client-side passphrase combined with PBKDF2 or Argon2id to derive encryption keys.
  • Asymmetric Public Key Sharing: Integrating Web Crypto RSA-OAEP/ECDH to allow targeting specific recipient public keys.
